**A pure-Go (no cgo) FFT library** — the `numpy.fft` / `scipy.fft` equivalent for
Go. It computes the discrete Fourier transform of complex and real signals of
**any length**, with no dependency on the native FFTW3 C library.

Ruby has no cgo-free FFT (every option wraps FFTW3); `gonum/dsp/fourier` is pure
Go but its optimized assembly is amd64-only. go-fft is a portable Go core that
runs on Go's six 64-bit targets, with **AVX2 and AVX-512 kernels on amd64**
generated by go-asmgen and **bit-identical** to the Go code. It is grown
test-first with **100% coverage** and differentially checked against `numpy.fft`.

```go
import "github.com/go-fft/fft"

x := []complex128{1, 2, 3, 4}
X := fft.FFT(x)          // forward transform
y := fft.IFFT(X)         // round-trips back to x
```

## API surface

| Area | Functions |
| --- | --- |
| Complex 1-D | `FFT`, `IFFT` |
| Real 1-D | `RFFT`, `IRFFT`, `FFTReal` |
| Multi-dimensional | `FFTN`, `IFFTN`, `FFT2`, `IFFT2`, `RFFT2`, `IRFFT2` |
| Frequency bins | `FFTFreq`, `RFFTFreq` |
| Windows | `Hann`, `Hamming`, `Blackman`, `BlackmanHarris`, `Bartlett` |
| Spectral | `PSD`, `Spectrogram` |
| Reusable plans | `NewPlan`, `NewRealPlan`, `NewPlanN`, `NewRealPlan2` |

Normalization, bin layout and frequency conventions follow `numpy.fft`.

### Reusable plans

A plan computes the twiddle tables once and reuses them, so a transform does no
`sin`/`cos`. The convenience functions above keep an internal per-length plan
cache and get this for free. A plan is what you reach for when you control the
loop: it writes into your slice, so a repeated transform allocates nothing.

```go
p := fft.NewPlan(n)            // complex transform of length n
p.FFT(dst, src)                // []complex128 of length n; dst and src may alias
p.IFFT(dst, src)               // normalized inverse

rp := fft.NewRealPlan(n)       // real-input transform
rp.RFFT(dst, src)              // src []float64 (n), dst []complex128 (n/2+1)
rp.IRFFT(out, spec)            // out []float64 (n), spec the half spectrum

pn := fft.NewPlanN(rows, cols) // any rank: NewPlanN(d0, d1, d2, ...)
pn.FFT(dst, src)               // row-major; matches FFTN
r2 := fft.NewRealPlan2(rows, cols)
r2.RFFT(spec, img)             // spec len r2.SpectrumLen() = rows*(cols/2+1)
```

`FFTN`, `FFT2` and `RFFT2` return a new slice on every call. On a many-core
host, that allocation (and the garbage collector behind it) can cost more than
the transform itself for a small repeated shape; `PlanN` and `RealPlan2` avoid it.

## How a length is transformed

* **Lengths whose prime factors are all ≤ 13**: an iterative mixed-radix
  **Stockham** engine, with radix-8/4/2/3/5/7 straight-line passes plus a
  general radix-p pass for 11 and 13.
* **A prime whose N−1 is 7-smooth**: **Rader's algorithm**. **Any other length**:
  **Bluestein's chirp-z**. Both convolve on the Stockham engine.
* **Powers of two on loong64, s390x and amd64 without AVX2, and above 65536
  on riscv64**: an
  iterative, cache-blocked **radix-4 kernel** (SSE2 butterflies on amd64).
* **Real transforms**: a half-length complex transform plus one untangle pass.
* **N-D transforms**: separable, with the lines of a large axis spread across
  cores.

## SIMD and architectures

* **amd64:**
  * **AVX2:** the Stockham passes of radix 2/3/4/5/8 run as generated AVX2
    kernels, with a final pass vectorized across blocks, and so does the real-FFT
    untangle.
  * **AVX-512:** powers of two of 256 points or more run four points per
    register, where the CPU and the operating system support it.
  * **Without AVX2:** the radix-4 kernel runs SSE2 butterflies.
* **arm64, riscv64, loong64, ppc64le, s390x:** the passes are Go code, which the
  gc compiler compiles to scalar instructions. It does not vectorize; it does
  fuse multiply-adds.
  * **Complex multiply:** kernels for arm64 (NEON), riscv64 (RVV) and s390x
    exist and are validated bit-identical, but are not used, because the scalar
    loop measured as fast.
  * **Stockham passes:** a NEON prototype measured about 10% per transform on
    Neoverse-N1, not enough to ship yet.

⛔ The amd64 kernels keep the Go code's arithmetic order exactly: separately
rounded multiplies and adds, no FMA, no reassociation. Their results are
therefore **bit-identical** to the Go passes. The tests check it on generic,
signed-zero and infinite inputs, comparing `math.Float64bits`. A faster
transform that answers differently is not the same transform.
