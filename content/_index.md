**A pure-Go (no cgo) FFT library** — the `numpy.fft` / `scipy.fft` equivalent for
Go. It computes the discrete Fourier transform of complex and real signals of
**any length**, with no dependency on the native FFTW3 C library.

Ruby has no cgo-free FFT (every option wraps FFTW3); `gonum/dsp/fourier` is pure
Go but its optimized assembly is amd64-only. go-fft is a portable Go core that
runs on Go's six 64-bit targets, with **AVX2 and AVX-512 kernels on amd64** and
**NEON kernels on arm64**, generated by go-asmgen and **bit-identical** to the Go
code. It is grown
test-first with **100% coverage** and differentially checked against `numpy.fft`.

```go
import "github.com/go-fft/fft"

x := []complex128{1, 2, 3, 4}
X := fft.FFT(x)          // forward transform
y := fft.IFFT(X)         // round-trips back to x
```

**Try it in your browser:** the [playground](https://go-fft.github.io/playground/) runs go-fft compiled to
WebAssembly, with nothing to install — pick a signal and a transform (FFT, RFFT, DCT/DST, any length, float64 or float32), see the spectrum, and copy the equivalent Go and numpy code.

**Use v0.26.3 or later.** v0.25.0 to v0.26.2 return wrong N-D results, silently,
on Intel CPUs with AVX-512 when an axis other than the last has a length 9·p
([v0.26.3 release notes](https://github.com/go-fft/fft/releases/tag/v0.26.3)).

Normalization (`Norm`: `NormBackward`, the default, `NormOrtho`, `NormForward`),
bin layout and frequency conventions follow `numpy.fft`; the DCT and DST follow
`scipy.fft`.

### Opt-in fused multiply-add (`Options.FMA`)

By default every amd64 kernel is bit-identical to the package's Go code for the
route it runs: the same machine and route give the same bits, and every route
stays within the stated bound. Different amd64 CPUs can choose different routes
for some lengths (165 of 417 cases differ at v0.28.16), so the bits are not
promised to match across CPUs. `Options{FMA: true}` gives
that up for speed on amd64 CPUs with FMA3: twiddle products and butterfly
constants are fused, and on AVX-512 Intel CPUs (Cascade Lake) 1,024 and 2,048
points take radix-32 passes. Results differ from the default's in the last
bits and are as accurate (0.76–1.08× the default's error against long-double
scipy, over 90 transforms). Elsewhere (arm64, other architectures, no FMA3)
the option gives the default transform, bit for bit; the float32 transforms
ignore it.

```go
X := fft.FFTWith(x, fft.Options{FMA: true})
p := fft.NewPlanWith(1024, fft.Options{FMA: true})
```

Use it when bit-for-bit reproducibility across machines does not matter.
Measured gains against the default plan: Cascade Lake complex 1,024 1.22×
(0.94× FFTW's time, against 1.19× by default; re-measured 2026-11-07 at
v0.28.11: 1.03× against 1.24×), 2,048 1.11×, RFFT 4,096 1.09×,
256 and 512 1.07–1.08×; Zen 3 1–6% (complex 1,024 stays 1.10× FFTW's time).
Where fusing measured slower (Cascade Lake 4,096 to 16,384 points) the plan
keeps the default kernels, so no measured row is slower than the default. See
[Performance](performance/).

### Reproducible bits (`Options.Exact`, v0.29.0)

go-fft's contract is an error bound against an extended-precision result: the
relative RMS error is at most `c·ε·log2(n)`, with `c` between 0.5 and 2.25 per
function family (measured, not proved; the worst ratio seen is 1.03), checked
against a double-double oracle in both precisions, with and without
`Options.FMA`; it is not bit identity with another implementation.
`Options{Exact: true}` names the package's reference arithmetic for callers
who need the last bits to be reproducible: the reference arithmetic as
compiled by gc (the SIMD kernels round every multiply and add separately; on
arm64 gc fuses multiply-adds in the Go reference, so amd64 and arm64 differ),
in the reference's order of operations: the bits of v0.28.16 on the same
machine. It does not promise the same bits on every CPU, because v0.28.16
itself gave different bits on different amd64 CPUs for some lengths
([#121](https://github.com/go-fft/fft/issues/121)). Every `...With` function (float32
included) and `NewPlanWith`, `NewRealPlanWith`, `NewPlanNWith`,
`NewRealPlan2With` accept it; it excludes `FMA` (both set panics).

```go
X := fft.FFTWith(x, fft.Options{Exact: true})
p := fft.NewPlanWith(1024, fft.Options{Exact: true})
```

Today the default is this arithmetic, so `Exact` changes nothing. A later
release may let the default fuse multiply-adds or reorder its kernels inside
the bound; `Exact` keeps the reference bits available whatever the default
becomes. The constants and the method are in the repository's
[docs/accuracy.md](https://github.com/go-fft/fft/blob/main/docs/accuracy.md).

### Float32 data with float64 accuracy (`...Mixed`, v0.30.0)

An audio codec holds its samples and coefficients in `float32`, and a float32
MDCT plan computes in float32: its worst relative RMS error measured at 1.9e-7,
short of what some codecs need. The mixed methods are on the existing float64
plans (no new plan type): `MDCTPlan.MDCTMixed` and `IMDCTMixed`, and, for a
DCT-IV plan, `DCTPlan.DCTMixed` and `IDCTMixed` (any other DCT type panics
with an `fft:` message). The `float32` input is converted to `float64` while
the pre-twiddle reads it, together with the MDCT's fold; the arithmetic is
float64; the single rounding to `float32` happens while the post-twiddle
writes, together with the unfold. There is no extra pass and no allocation, `dst` may overlap
`src`, and the plans stay safe for concurrent use. The result is exactly
`float32` of the float64 path, bit for bit (asserted by `TestMixedIsFloat32OfFloat64`
and a fuzz target). `scale` is a `float64`, as in `MDCT`.

```go
p := fft.NewMDCTPlan(2048)
p.MDCTMixed(coef, samples, scale) // float32 in and out, float64 inside
```

The name says what it is: the `...32` suffix in this package means float32
*arithmetic* (`DCT32`, `MDCTPlan32`), so a `DCT32` method on a float64 plan
would say the opposite.

Accuracy, in relative RMS against the double-double oracle:
`err <= c64·ε64·log2 n + ε32/2`.

| Transform | c64 | Worst error, as a fraction of the bound |
|:--|--:|--:|
| MDCT | 1.75 | 0.56 |
| DCT-IV | 2.0 | 0.84 |

Time per call (Apple M4 Max, one core, ns; from go-fft#143):

| | mixed | float64 + two manual conversions | float32 plan |
|:--|--:|--:|--:|
| DCT-IV, M = 128 | 156 | 226 | 164 |
| DCT-IV, M = 1024 | 1204 | 1704 | 1159 |
| MDCT, N = 256 | 172 | 278 | 161 |
| IMDCT, N = 256 | 178 | 284 | 166 |
| MDCT, N = 2048 | 1402 | 2147 | 1199 |
| IMDCT, N = 2048 | 1409 | 2187 | 1215 |

The mixed methods are 29 to 38 percent faster than float64 with manual
conversions, and take 0.95 to 1.17 times the float32 plan's time while keeping
float64 accuracy.

The MDCT itself got faster in v0.29.1 (go-fft#136): for an even `n/2` it fuses
the fold into the DCT-IV's pre-twiddle and the unfold into its post-twiddle,
with one scratch of `n/4` complex values, and a one-slot scratch cache sits in
front of the `sync.Pool`. MDCT / IMDCT at 128 samples went from 143 / 133 ns to
96 / 93 (FFTW's REDFT11 plus the same fold: 87 / 87), at 256 from 231 / 228 to
163 / 169 (162 / 165), at 2,048 from 1,715 / 1,689 to 1,331 / 1,344 (1,770 /
1,700); float32 at 128 from 125 / 124 to 80 / 85. The float64 MDCT at 128
samples is still 1.07 to 1.10 times FFTW's time.

#### SIMD twiddle passes and the first dependency (v0.30.1)

The DCT-IV and DST-IV (and `DCTMixed`/`IDCTMixed`) run both their pre- and
post-twiddle passes on the
[go-simd/floats](https://github.com/go-simd/floats) v0.18.0 kernels
(`CMulGather`, `CMulScatter` and the float32-data forms; NEON on arm64,
AVX2+FMA on amd64, portable loops elsewhere), following the rule of one
implementation in the lowest shared library. The MDCT and IMDCT (and their
Mixed forms) use them for one of their two twiddle passes only: the
post-twiddle for the MDCT, the pre-twiddle for the IMDCT; their other pass is
the fold or the unfold, still a Go loop. go-fft's `go.mod` now requires
`github.com/go-simd/floats v0.18.0` and, under it, `golang.org/x/sys` (CPU
detection); govulncheck reports nothing. `DCTPlan32` and `MDCTPlan32` compute
in float32 and are unchanged. The kernels fuse multiply-adds, so the default
DCT, DST and MDCT bits changed in the last places, inside the stated bound.

**`Options.Exact` does not cover the DCT, DST and MDCT plans**: they take no
`Options`, and their twiddle passes are the SIMD kernels, so there is no exact
mode for them yet (it is part of the third arithmetic of
[go-fft#121](https://github.com/go-fft/fft/issues/121), step 3).

Time per call (Apple M4 Max, one core, interleaved, ns, medians of 6; FFTW
3.3.10 `REDFT11` in place plus the same fold, `FFTW_MEASURE`):

| | v0.30.0 | v0.30.1 | FFTW |
|:--|--:|--:|--:|
| DCT-IV, M = 64 | 87.0 | 88.0 | 78.6 |
| DCT-IV, M = 128 | 149.5 | 141.7 | 143.3 |
| DCT-IV, M = 256 | 305.4 | 272.7 | 320.8 |
| DCT-IV, M = 1024 | 1164 | 1038 | 1442 |
| DCTMixed, M = 128 | 154.9 | 138.2 | |
| DCTMixed, M = 1024 | 1218 | 1050 | |
| MDCT / IMDCT, N = 128 | 91.4 / 97.9 | 87.0 / 98.1 | 87.4 / 88.1 |
| MDCT / IMDCT, N = 256 | 165.4 / 174.8 | 158.2 / 170.7 | 165.8 / 169.5 |
| MDCT / IMDCT, N = 2048 | 1346 / 1366 | 1258 / 1299 | 1715 / 1669 |

The DCT-IV gains 0 percent at 64 points, 5 percent at 128, and 11 percent at
256 and 1,024; the mixed form 9 to 14 percent; the MDCT 4 to 7 percent and the
IMDCT 0 to 5 percent (its unfold is still a Go loop). Against FFTW the DCT-IV
is 1.12 times at 64 points, level at 128 and faster from 256 on; the forward
MDCT is level at 128 and 256 and faster at 2,048; the IMDCT is 1.11 times
FFTW's time at 128 samples (98.1 against 88.1 ns), level at 256 and faster at
2,048. On an AMD Ryzen 9 7950X (Zen 4; one core, AVX2 kernels, against FFTW
3.3.10's AVX-512 build, v0.30.1; method and the complete table with scipy in
[go-fft#132](https://github.com/go-fft/fft/issues/132#issuecomment-6863019790))
the DCT-IV at 64, 128, 256 and 1,024 points takes 61, 102, 182
and 762 ns against FFTW's 88, 177, 555 and 2,130, the MDCT at 128 samples 85
ns against 105, and the IMDCT 91 against 113; go-fft is faster than FFTW on
every row measured there.

#### MDCT fold/unfold kernels and a faster Spectrogram (v0.30.2)

- **MDCT and IMDCT.** The fold (before the DCT-IV's gather) and the unfold
  (after its scatter) now run the go-simd/floats v0.19.0 kernels `MDCTFold` and
  `MDCTUnfold` (and the float32-data forms for the Mixed methods): the MDCT
  from 512 to 4,096 samples, the IMDCT from 256 to 4,096. Outside those
  windows the fused Go loops stay, because they are faster or equal (at 128
  samples) or the kernels lose 3 to 7 percent (from 6,144 samples). On an
  Apple M4 Max (6 interleaved rounds at load 5.5 to 7.6, against v0.30.1)
  the MDCT / IMDCT times are 0.94 / 0.93 of v0.30.1's at 512 samples, 0.91 /
  0.92 at 1,024, 0.92 / 0.90 at 2,048 and 0.97 / 0.97 at 4,096 (the IMDCT
  also 0.94 at 256 and 384); at 128, 6,144 and 8,192, outside the window, the
  medians are within 4 percent of v0.30.1's. `MDCTPlan32` computes in float32 and
  keeps its Go loops. The kernels fuse multiply-adds, so the bits differ in the
  last places inside the stated bound.
- **`Spectrogram`.** The window multiply uses `floats.Mul` and the power pass
  `floats.SquaredMagnitude` (go-simd/floats v0.20.0). For 16,384 samples,
  segment 256, overlap 128, one core: Zen 4 28.0 µs, from 38.8, against FFTW
  3.3.10's `many_dft_r2c` at 25.4 (1.10 times, from 1.53); Apple M4 Max 40.8
  µs, from 51.4. The gap is the real FFTs (16.6 µs) and the result allocation
  (4.6 µs). The gain on x86 comes from `Mul` and `SquaredMagnitude`: a third
  path that folds the window into the real-FFT packing gather exists, but it
  only runs on loong64 and s390x (and above the Stockham ceiling), so it is
  not what speeds up amd64 or arm64. On amd64 about 16 percent of the power
  values differ by one ulp from before, because the kernel uses FMA; arm64 is
  bit-identical. `PSD` and `Spectrogram` stay inside the `psd` row of the
  accuracy bound.

### Reusable plans

A plan computes the twiddle tables once and reuses them, so a transform does no
`sin`/`cos`. The convenience functions above keep an internal per-length plan
cache and get this for free. A plan is what you reach for when you control the
loop: it writes into your slice, so a repeated transform allocates nothing.

```go
p := fft.NewPlan(n)            // complex transform of length n
p.FFT(dst, src)                // []complex128 of length n; dst and src may alias
p.IFFT(dst, src)               // normalized inverse

rp := fft.NewRealPlan(n)       // real-input transform
rp.RFFT(dst, src)              // src []float64 (n), dst []complex128 (n/2+1)
rp.IRFFT(out, spec)            // out []float64 (n), spec the half spectrum

pn := fft.NewPlanN(rows, cols) // any rank: NewPlanN(d0, d1, d2, ...)
pn.FFT(dst, src)               // row-major; matches FFTN
r2 := fft.NewRealPlan2(rows, cols)
r2.RFFT(spec, img)             // spec len r2.SpectrumLen() = rows*(cols/2+1)
```

`FFTN`, `FFT2` and `RFFT2` return a new slice on every call. On a many-core
host, that allocation (and the garbage collector behind it) can cost more than
the transform itself for a small repeated shape; `PlanN` and `RealPlan2` avoid it.

## How a length is transformed

* **Lengths whose prime factors are all ≤ 13**: an iterative mixed-radix
  **Stockham** engine, with radix-8/4/2/3/5/7 straight-line passes plus a
  general radix-p pass for 11 and 13.
* **A prime whose N−1 is 7-smooth**: **Rader's algorithm**. **Any other length**:
  **Bluestein's chirp-z**. Both convolve on the Stockham engine.
* **Powers of two on loong64, s390x and amd64 without AVX2, and above 65536
  on riscv64**: an
  iterative, cache-blocked **radix-4 kernel** (SSE2 butterflies on amd64).
* **Real transforms**: a half-length complex transform plus one untangle pass.
* **N-D transforms**: separable, with the lines of a large axis spread across
  cores. On amd64 with AVX2, an axis other than the last runs as batched passes
  over strips of neighbouring lines, in place, instead of gathering each line.

## SIMD and architectures

* **amd64:**
  * **AVX2:** the Stockham passes of radix 2/3/4/5/8 run as generated AVX2
    kernels, with a final pass vectorized across blocks, and so does the real-FFT
    untangle.
  * **AVX-512:** powers of two of 256 points or more run four points per
    register, where the CPU and the operating system support it. From 65536
    points on Intel, a blocked schedule keeps the last passes in L2 (v0.12.0).
  * **Radix 16:** on AVX2 without AVX-512, 128, 256 and 1024 points (2048 on
    Intel) take a radix-16 pass (v0.10.0).
  * **Split layout (AMD, AVX2):** powers of two keep real and imaginary parts
    apart between passes, removing every shuffle (v0.14.0).
  * **Composites (Intel, AVX2):** a radix-12 prime-factor pass and radix-16
    tails up to 16384 points (v0.15.0); on AMD, radix-10/12/15/20 prime-factor
    passes (v0.18.0).
  * **Split layout at 512 bits (Intel, AVX-512):** powers of two from 256
    points, eight points per register (v0.19.0).
  * **Without AVX2:** the radix-4 kernel runs SSE2 butterflies.
* **arm64:** the Stockham passes of radix 2/3/4/5/8, and the radix-2 to 5 final
  passes over an even number of blocks, run as generated **NEON** kernels
  (1.28× per transform on Neoverse-N1, 1.15× on Apple M4). gc fuses
  multiply-adds on arm64, so each kernel reproduces which product the Go code
  rounds and which it fuses. Powers of two keep their data split between
  passes, and the columns of N-D plans run as batched NEON passes (v0.11.0).
  The real-FFT untangle has a NEON kernel, and small N-D plans run each axis as
  one pass sequence over all lines (v0.17.0).
* **Single precision:** the float32 passes, the real-FFT untangle and the N-D
  column passes have their own AVX2 and NEON kernels (v0.13.0, v0.16.0).
* **riscv64, loong64, ppc64le, s390x:** the passes are Go code, which the gc
  compiler compiles to scalar instructions. It does not vectorize; it does fuse
  multiply-adds.
  * **Complex multiply:** kernels for riscv64 (RVV) and s390x exist and are
    validated bit-identical, but are not used, because the scalar loop measured
    as fast.

⛔ The kernels keep the Go code's arithmetic exactly: on amd64 separately
rounded multiplies and adds, no FMA, no reassociation; on arm64 the same
fusions gc chose. Their results are therefore **bit-identical** to the Go passes
(except the bits of a NaN produced from infinite inputs, which IEEE 754 leaves
unspecified). The tests check it on generic,
signed-zero and infinite inputs, comparing `math.Float64bits`. A faster
transform that answers differently is not the same transform.
